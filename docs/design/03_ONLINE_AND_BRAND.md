# オンライン・X共有・企業PRの仕様

## 1. Xへの投稿

基本動線は「結果を確認 → Xにポスト → Xの投稿画面で本人が投稿」。自動投稿やXログインをゲーム開始の条件にしない。

投稿文の例：

```text
目玉焼き、今日は96点！
白い卵 × とろりで「理想のひと皿！」
あなたは何点？
#たまご日和 #目玉焼きチャレンジ
[公開ゲームURL]
```

`https://x.com/intent/tweet` にtext、url、hashtagsをURLSearchParamsで設定する。hashtagsは「#」を除くカンマ区切り。公開URLは設定値から取得し、未設定時は付けない。最終の文面や改行が投稿画面でどう引き継がれるかを公開前に実機確認する。

Web IntentだけでローカルPNGを添付する仕様にはしない。次の手段を並べる。

| 手段 | ユーザーの操作 | 留意点 |
|---|---|---|
| Xにポスト | テキストとリンクを持ってXへ | 画像の自動添付は前提にしない |
| 画像を保存 | 結果PNGを保存し、Xで添付 | downloadが機能しない環境では画像を開き保存方法を案内 |
| 画像を共有 | OSの共有画面から送信先を選ぶ | HTTPS、share/canShareの有無、ファイル対応を検出。Xが選べるとは限らない |
| 結果の文をコピー | 投稿文をクリップボードへ | Clipboard不可なら選択できるテキストを表示 |

結果画面で先にPNG Blob/Fileを用意し、ユーザーのタップから直ちにnavigator.shareを呼べるようにする。準備中は「画像を準備中」。長い非同期処理でユーザー操作の有効性を失わせない。canShare({files:[file]})でファイル対応を確認し、AbortErrorはキャンセル扱い、その他の失敗は保存へ誘導する。

実際の投稿完了はWeb Intentや共有画面の起動から判定できない。計測名は「投稿画面を開いた」「共有画面を開いた」とし、投稿数と呼ばない。

## 2. 結果画像

1200×630pxのPNG。安全余白48px。左約65%にそのプレイの卵と皿、右に点数、称号、卵種と目標、下にゲーム名と任意の提供ロゴ。画面のボタンや入力欄は含めない。

採点確定時のW/Y/B/Dとseedを保持し、同じ状態からオフスクリーンのシーンを描画して2D canvasに合成する。UIスクリーンショットをそのまま切り取らない。低メモリ端末では600×315に落として保存できる。日本語の文字描画はフォントの読込完了を待つ。

画像への公開名掲載は初期オフ。スコアがローカル未検証なら共有画像に順位を付けない。オンラインでも投稿時点の順位と取得時刻を示し、後に変化し得るものとして扱う。

外部の商品画像は同一オリジンで配信するかCORS対応を確認し、canvasが汚染されないようにする。画像読込失敗時は商品画像を省いて結果PNGを作る。常時preserveDrawingBufferを有効にして性能を落とさず、専用描画または描画直後のcaptureを用いる。

結果ごとの公開URL・動的OGPは後続拡張。導入する場合はサーバーで結果ページと公開画像を返し、クローラーがJavaScriptを実行しなくてもメタ情報を読めるようにする。初期は共通ゲームURLと画像保存で成立させる。

## 3. ランキングの構成

公開ランキングにはサーバーと永続DBが必要。localStorageは端末内の自己ベスト専用。

区分キー：scoringVersion + eggId + targetId + period。週間は日本時間の月曜00:00〜次の月曜00:00、全期間も用意する。日時はDBではUTCで持ち、画面と期間判定はAsia/Tokyo。週への所属はサーバー検証完了時刻で決める。

「週間・白い卵・とろり」など区分を常に明示。全種類を混ぜた優劣は初期には作らない。各匿名プレイヤーの区分内自己ベスト1件。匿名識別は同一人物を完全に識別できず、Cookie消去・別端末は別参加者になり得る。賞品付きキャンペーンを行う段階では本人確認等を別途設計する。

同点は同順位の競技順位方式：1、1、3。行の並びは先に達成したサーバー日時、最後にresultIdで安定化。週間切り替え後も古い記録を上書きしない。

## 4. APIとデータ

| API例 | 役割 |
|---|---|
| POST /api/runs | eggId/targetIdを受け、runId・seed・scoringVersion・有効期限を発行 |
| POST /api/runs/:id/finish | 操作ログと終了stepを受け、検証・再計算・結果固定。クライアントscoreは採用しない |
| POST /api/results/:id/publish | 同一セッションの結果を、表示名を確認して公開登録 |
| GET /api/leaderboard | 卵・目標・バージョン・期間で絞り、上位50件と自分の記録を返す |

公開名・ランキング掲載は任意。ゲームのスコア算出と公開登録を分ける。公開しない結果も手元で共有できる。

```text
players: id, createdAt, sessionCredentialHash
runs: id, playerId, eggId, targetId, seed, scoringVersion, startedAt, expiresAt, status
results: id, runId(unique), playerId, eggId, targetId, scoringVersion,
         W, Y, B, D, score, stopStep, verifiedAt, publishedAt(nullable), displayName(nullable)
events: runId, seq, step, action, value  // 必要な検証期間だけ保持する運用を設ける
```

操作例：`{seq:0,step:240,action:"heat",value:"low"}`。stepは0以上5400以下の整数。actionはheat/lidのみ、停止はstopStep。pauseは調理stepを増やさない。暗号鍵をクライアントへ置かない。

## 5. 検証と保存

- セッションの匿名プレイヤーとrunをサーバーで紐付ける。別プレイヤーのrunを終了・公開できないこと。
- 有効期限は発行から15分を初期値。ネットワーク再試行は同じrunId・同じ操作ログを使用。
- seqは連番、stepは非減少、範囲内、操作は許可リスト。最大500イベント、同じ値の連続記録を除去する。多すぎる場合は正当な操作も含め失敗理由を明示。
- stopStepは最終イベント以上、5400以下。調理秒がサーバー実経過より不自然に長い場合は拒否。通信遅延の許容差は設定する。
- サーバー側の同じバージョンのモデルで初期状態から再生し、整数得点を確定。seed、卵、目標はrun発行時の値を使う。
- runId一意制約とトランザクションで二重登録を防止。同じfinishの再送は同じ結果を返し、異なるログへの差し替えは拒否。
- 名前は1〜12書記素、制御文字除去、文字列としてエスケープして表示。入力値をHTMLとして解釈しない。不適切名を非表示・修正できる運営手段を用意する。
- DBへの直接書込権限や秘密鍵をフロントに渡さない。CookieセッションならCSRF対策・SameSite等を設定。CORSとレート制限は公開先に合わせる。
- ローカル開始時にrunを発行できなかったプレイはローカル専用。通信復帰後に検証済み記録へ見せかけない。
- finishが失敗しても結果画面は保持。有効期限内は同じrunを再送可。期限切れはローカル結果として残す。

再計算は任意スコアの直送や不可能なログを防ぐが、成立する操作ログの自動生成や複数アカウントを完全には防げない。賞品付き運用では監視・参加制限など追加対策が必要。

## 6. 企業PR

ゲームで感じた「食べたい」を、正式な商品情報と購入先につなげる。ブランド未定のため設定はenabled:false。社名やリンクが無ければPR枠自体を非表示にする。

| 場所 | 表示 | 目的 |
|---|---|---|
| タイトル下部 | PR・提供：企業名、小さなロゴ | 提供関係を分かりやすくする |
| 卵選択 | 正式商品画像・商品名・承認済みの短い説明 | 商品に親しむ |
| 結果下部 | 今度は、本物のたまごで。＋商品カード＋購入先 | 興味が高まった時に案内 |
| シェア画像端 | 小さな提供ロゴ（設定時のみ） | 結果を主役にした認知拡大 |

課金や広告視聴による得点優遇は入れない。購入をランキング参加の条件にしない。食材の健康効果、殻色による栄養差、根拠のない品質表示は足さない。生成した卵画像を実在商品写真として扱わない。レシピは企業の確認済みページにリンクする。

## 7. 計測

| イベント | 確認したいこと |
|---|---|
| game_start | 何人が調理を開始したか |
| egg_select | 卵の選択比率 |
| game_complete | 完了率、点数分布 |
| replay_start | もう一度遊ばれているか |
| result_image_save_click | 画像保存の操作が使われたか |
| x_intent_open | X投稿画面へ進んだか |
| native_share_open | OSの共有画面へ進んだか |
| leaderboard_publish | 公開登録まで進んだか |
| sponsor_click | 商品ページへ進んだか |

同じrunの完了は一度だけ計測。クリックは実際の保存成功・投稿成功・購入成功を意味しない。企業PRの成果はまず完了率、再挑戦率、商品クリック率で評価し、売上との因果関係を断定しない。氏名、メール、位置情報はゲーム開始に不要。運用する計測サービスや保存期間は公開前に設定し、案内ページに反映する。

## 8. 技術資料（2026-09-27確認）

- Three.js WebGLRenderer：WebGL 2使用、r163以降WebGL 1非対応。
  https://threejs.org/docs/pages/WebGLRenderer.html
- MDN Web Share API：共有は対応環境・HTTPS・ユーザー操作等の条件がある。
  https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API
- MDN Navigator.share / canShare：ファイル共有の判定と送信。
  https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share
  https://developer.mozilla.org/en-US/docs/Web/API/Navigator/canShare
- X公式Publish：投稿リンクの入口と現在の公式ボタンを確認する。
  https://publish.x.com/

Xの旧Web IntentドキュメントURLは確認時に概要ページへ転送されたため、公開実装時に生成リンクを実機で再確認する。画像の直接添付を想定せず、保存とOS共有を別経路にする方針。
